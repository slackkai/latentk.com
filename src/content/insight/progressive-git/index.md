你已经会 `git add .`，也会 `git commit -m "..."`。文件改了几天，一切顺利。直到一次 push 被拒绝，或者切分支时文件忽然变了，才发现：能记住那两条命令，还不足以解释眼前发生的事。

问题不在命令多，而在于没有一个大到能装下它们的模型。这份教程按「先会用、再理解模型、最后处理复杂情况」的路线走，把 Git 拆成七课，每课配一个能直接敲命令的沙盒：上面画着工作区、暂存区和提交图，你敲一条命令，它们就实时变一次。沙盒是浏览器里的纯模拟，不碰你电脑上的任何东西。

:::postit[沙盒使用说明]{tip}
任务条里的命令点一下就会填进终端；终端支持 **Tab** 补全、**↑ ↓** 翻历史、`help` 看命令表；卡住了点「提示」，搞砸了点右上角「↺ 重来」。每课完成时会出现「下一课」按钮。

不熟悉 `cd`、`cat` 的话，可以先去[命令行入门](../linux-cli/index.md)走一圈。
:::

读完你手里会有三样东西：一套每天都要用的命令循环、一张能解释分支和远程的图、一组处理麻烦事的急救手段。

## 第 1 课：给文件夹拍快照

Git 把一个文件夹在某一刻的样子整体存下来，存成一张快照，叫做**提交**（commit）。仓库（repository）就是装着所有快照的房间——`git init` 做的事，只是在文件夹里建了一个 `.git` 目录。

但 Git 不希望你随手就拍。它在你的文件和提交之间放了一个**暂存区**：`git add` 决定「下一次快照里装什么」，`git commit` 才真正拍下去。多这半步的意义是，你可以把一堆乱糟糟的修改，挑成一笔干净的提交。

:::layout{wide}
::embed[第 1 课的沙盒：从 mkdir 到第二张快照，跟着任务敲。]{page=./attachments/sandbox-1}
:::

这一课的关键词是**工作区**、**暂存区**、**提交**。记住日常循环：`status` 看一眼 → `diff` 看改了什么 → `add` 挑内容 → `commit` 拍快照 → `log` 看历史。

沙盒里你会先 add，再往同一份文件追加一行。暂存区记下的是 add 那一刻的内容，不会跟着原稿一起变。`git diff` 看工作区比暂存区多了什么，`git diff --staged` 看下一次提交准备装什么。:note[git status 和 git diff 都是只读的，任何时候都可以放心敲；不知道该干什么的时候，先看一眼总是划算的。]

## 第 2 课：分支是一张会移动的便签

历史不是一条直线，而是一张图：每个提交都记着自己是从哪个提交来的。**分支**（branch）只是贴在某个提交上的一张便签，默认那张叫 `main`；**HEAD** 是「你现在站在哪张便签上」的记号。

创建分支不复制任何文件，切换分支也不神秘：Git 把工作区换成目标快照的样子，再让 HEAD 跟过去。所以同一个文件在不同分支上可以有不同的内容——第三章只在 `draft` 的提交里，不在 `main` 的提交里。

当一条分支没有走远时，合并只需要把便签往前挪一格，这叫**快进**（fast-forward）。

切回 `main` 的时候，第三章会消失吗？:pen[会。文件跟着 HEAD 走，工作区被换成 main 那张快照。但提交一张都没丢——切回 draft，它就在那里。]{hide}

:::layout{wide}
::embed[第 2 课的沙盒：创建分支、提交、切回、快进合并、删分支。]{page=./attachments/sandbox-2}
:::

一句话概括这一课：**分支是便签，不是副本**。删除一个已经合并的分支，不会删除任何提交；它只是撕掉一张便签。

:::fold[切换前，桌上还有没收好的东西]
这课先把修改提交好再切换。真实 Git 有时会让未提交的修改跟着走，有时会因为目标分支可能覆盖它们而拒绝。遇到拒绝，先看 status、保存手头工作，不必强行切换。

`main` 也不是每个仓库固定的名字，以你看到的分支名为准。HEAD 还能直接指向某个提交；等确实遇到这种情况，再认识 detached HEAD 也不迟。
:::

## 第 3 课：冲突是 Git 不敢替你做的决定

两个人（或者两个你）改了同一处，就会冲突。合并时 Git 先找到双方的共同祖先，再把两边的改动叠上去；只有两边改了同一处、又没有一致的新版本时，它才停下来。所以**冲突不是故障**，是 Git 在说：这个决定该由人来做。

冲突文件里会出现三行标记：`<<<<<<<` 和 `=======` 之间是你的版本，`=======` 和 `>>>>>>>` 之间是对方的版本。删掉标记、留下想要的内容，再 `git add`，就等于告诉 Git「这处解决了」。

:::layout{wide}
::embed[第 3 课的沙盒：制造一场冲突，然后在编辑器里解决它。]{page=./attachments/sandbox-3}
:::

沙盒里的合并收尾不用写说明，Git 会生成一句默认的合并说明；真实终端里的 `git commit` 可能先打开编辑器，让你确认这句说明。合并提交有两个父提交，所以提交图上出现一个 Y 字。记住解决冲突的三步：**改文件 → `git add` → `git commit`**。`add` 表示你处理好了，不表示 Git 已经替你检查过答案。

:::fold[冲突太多，不想解了]
`git merge --abort` 会把工作区恢复成合并开始前的样子，连已经 add 过的解决结果也会一起回退。开始前如果混着未提交修改，它不一定能完整还原现场，所以从干净工作区开始合并更稳妥。
:::

## 第 4 课：克隆、提交、推送

到这一课为止，一切都在本地。Git 的协作模型里，服务器上的仓库和你的仓库没有本质区别，只是大家约定以它为准。**克隆**（clone）一口气做三件事：把提交对象复制下来、把服务器地址记成 `origin`、把默认分支的上游（upstream）设好。

有一条最容易误会的概念：`origin/main` 不是网络上的 main，而是「你上一次和 GitHub 交谈时，对方的 main 在哪」的**本地书签**。push 成功时它跟着更新；别人推了东西，它不会自己知道——第 5 课就专门处理这个时差。

:::layout{wide}
::embed[第 4 课的沙盒：左右两栏分别是你和 GitHub，看 push 如何移动双方的分支。]{page=./attachments/sandbox-4}
:::

`git clone`、`git push`、`git pull` 是日常出现频率最高的远程命令。第一次推送一个新分支用 `git push -u origin <分支>`，`-u` 会把上游记下来，以后在这个分支上直接 `git push` 就行。

:::fold[离开沙盒，第一次连接 GitHub]
真实连接还需要配置 HTTPS 或 SSH 认证。不要把 token 写进笔记或提交；沙盒不需要任何真实凭据。

`git remote -v` 看地址，`git branch -vv` 看跟踪关系。提交成功、推送成功和网站部署成功，是三件不同的事。
:::

## 第 5 课：别人也在推

协作真正的日常：你克隆之后，别人也推了东西。这时 `git push` 会被拒绝，因为你的 `main` 和 GitHub 上的 `main` 已经分叉。**拒绝不是坏事**——它是防止你覆盖别人工作的闸门。认证失败、网络问题和分支保护也会拒绝 push，读报错，不要一律当成历史分叉。

`fetch` 和 `pull` 的区别值得说清楚：在本课的普通远程配置下，`fetch` 拿回新提交、更新 `origin/main` 这个书签，不改工作区和当前本地分支；`pull` 先 fetch，再按选定策略整合。默认行为受 Git 版本和配置影响，不必猜：只接受快进用 `git pull --ff-only`，保留合并用 `git pull --no-rebase`，重放本地提交用 `git pull --rebase`。本课选最后一种，把尚未共享的提交逐个接到远端历史之后。改动需要重新检查，提交也有了新的身份。

:::layout{wide}
::embed[第 5 课的沙盒：先点「队友推送了一个提交」，再体验一次被拒绝的 push。]{page=./attachments/sandbox-5}
:::

:::postit[push 被拒绝时不要强推]{warn}
条件反射地 `--force` 会把远端已有的提交丢掉，别人的工作可能就没了。本课这种历史分叉的正确动作是：`fetch` → 看清分叉 → 合并或变基 → 再推送。强推只在完全属于你的分支上、并且你确定没人基于它工作时才考虑。
:::

:::fold[pull --rebase 之外的选择]
分叉时的三种收法：

1. `git pull --no-rebase`：产生一个合并提交，历史先分叉、再合拢。
2. `git pull --ff-only`：只允许快进，一旦分叉就报错，逼你显式处理。
3. `git pull --rebase`：获取后重放本地提交，适合还没有别人依赖的个人工作。

没有绝对正确的选项；团队用哪种，就跟着用哪种。rebase 遇到冲突时，改文件、`git add`，再 `git rebase --continue`；要取消用 `git rebase --abort`。它和普通 merge 的收尾命令不一样。
:::

## 第 6 课：后悔药

后悔药按「东西在哪个阶段」分几层，先分清阶段再选命令：

- 还在**工作区**：`git restore <文件>` 丢掉没暂存的修改。没指定来源时，它从暂存区恢复；本课里暂存区正好和最近一次提交一样。
- 在**暂存区**：`git restore --staged <文件>` 把它拿出来，文件本身保留。
- 已提交但**没推送**：`git commit --amend` 改写最后一次提交，也会带上当前暂存区里的内容；`git reset` 把分支指针往回挪。
- 已经**推送**：`git revert <提交>` 生成一个反向提交，历史不动，适合公开的分支。
- **找不到**提交了：`git reflog` 记得 HEAD 的每一次移动。先 `git show` 核对，再 `git branch rescue <哈希>` 贴一张便签；不必急着再 `reset --hard`。

本课按提交移动分支的 `reset` 有三种模式：`--soft` 只挪分支指针，暂存区和工作区保留；`--mixed`（默认）还把暂存区对齐到目标提交，工作区保留；`--hard` 连工作区一起对齐，未提交的已跟踪修改会被丢弃，还可能清掉挡路的未跟踪文件。这里“对齐暂存区”不是把文件全删掉，而是让它保存目标提交的版本。

:::layout{wide}
::embed[第 6 课的沙盒：从 restore 一路练到用 reflog 找回被 reset 掉的提交。]{page=./attachments/sandbox-6}
:::

:::postit[reset --hard 有两副面孔]{warn}
它既能「回到某个提交」，也能「销毁没提交的改动」。而且工作区里那部分连 `reflog` 都救不回来——reflog 记的是提交，不是你的草稿。它适合收拾本地还没分享的历史；已经推出去的提交用 `revert`。
:::

`reflog` 是这个工具箱里最像安全网的东西：它在本地记录 HEAD 等引用的更新，常能找出刚才离开的提交。:note[常见默认设置中，一般记录过期时间为 90 天，不可达记录为 30 天；配置和对象清理也会影响能否恢复。它不是长期备份，未提交的草稿也不在里面。]

## 第 7 课：把历史捋直

最后是三个整理手头工作的工具。**stash** 把没写完的已跟踪改动收进一个抽屉，之后 `stash pop` 再放回来。它保存工作区与暂存区的快照；新建、还没跟踪的文件默认不进去，需要时用 `git stash -u`。**rebase** 把你分支上的提交逐个重放到新的起点上，提交的哈希会变；内容大体还在，但新基底和冲突解决都要再检查。**cherry-pick** 从别的分支只摘一个提交的改动，比如把紧急修复带到自己的分支上。修复如果依赖别的提交，单摘这一笔可能还不够。

这三件事共同的前提是：你清楚自己在改写什么。rebase 之后，原来的提交还躺在 reflog 里，但别人如果已经拿到了旧版本，两条历史就对不上了。

:::layout{wide}
::embed[第 7 课的沙盒：stash 半成品、rebase 到最新主线、cherry-pick 一个修复。]{page=./attachments/sandbox-7}
:::

:::postit[已经共享的分支不要 rebase]{warn}
变基会替换提交。如果队友已经基于旧提交继续工作，你的新历史与他的起点就不再相同，可能出现重复提交或额外冲突。除非团队明确协调了改写，先只整理尚未共享的提交。
:::

:::fold[变基还是合并，怎么选]
只有自己在用、想让历史保持直线：**rebase**。多人共享的分支、或者想保留「这里发生过一次汇合」的记录：**merge**。团队可以约定在个人分支变基、在共享主线合并；关键是说清哪些历史允许改写，哪些需要保留。

`stash pop` 成功后会删掉那条记录；冲突时通常会留下。想更稳，可以先 `git stash apply`，检查后再 `git stash drop`。
:::

## 一张总表

| 场景 | 命令 | 说明 |
| --- | --- | --- |
| 开始一个仓库 | `git init` | 把当前文件夹变成仓库 |
| 看状态 | `git status` | 不知道干什么时，先敲它 |
| 看还没暂存的改动 | `git diff` | 工作区相对暂存区 |
| 看下一次提交 | `git diff --staged` | 提交前再确认一遍 |
| 挑内容进暂存区 | `git add <文件>` | `git add .` 含当前目录的删除；`-A` 覆盖整个仓库 |
| 拍快照 | `git commit -m "说明"` | 说明写「做了什么」，不是「改了什么文件」 |
| 看历史 | `git log --oneline --graph --all` | 历史是图，别只看一条线 |
| 开分支 / 切换 | `git switch -c <名字>` / `git switch <名字>` | 旧写法是 `checkout` |
| 合并 | `git merge <分支>` | 快进或生成合并提交 |
| 解决冲突 | 改文件 → `git add` → `git commit` | 反悔用 `git merge --abort` |
| 克隆 | `git clone <地址>` | 复制仓库 + 记住 origin |
| 推送 / 拉取 | `git push` / `git pull --rebase` | 新分支先 `push -u` |
| 只拿远端更新 | `git fetch` | 更新 `origin/main`，不动工作区 |
| 丢弃工作区改动 | `git restore <文件>` | 默认从暂存区恢复，会覆盖草稿 |
| 撤出暂存区 | `git restore --staged <文件>` | 文件保留 |
| 改写最后一次提交 | `git commit --amend -m "…"` | 别对已推送的提交用 |
| 回退本地历史 | `git reset --soft/--mixed/--hard <位置>` | `--hard` 会丢草稿 |
| 撤销已推送的提交 | `git revert <提交>` | 生成反向提交 |
| 找回丢失的提交 | `git reflog` → `git show` → `git branch rescue` | 先核对，再留入口 |
| 暂存半成品 | `git stash` / `git stash pop` | 未跟踪文件要加 `-u` |
| 换一个起点重放提交 | `git rebase <目标>` | 改写提交，别动共享分支 |
| 摘一个提交 | `git cherry-pick <提交>` | 只复制那一次改动 |

这张表不用背。用的时候回来查，或者在自己的仓库里敲一遍。`git add .` 很省事，刚开始用时写明文件名，更容易知道自己放上了什么。密钥、临时产物和大数据文件，留在快照外面。

## 离开沙盒前，试着解释三个结果

不再看命令表，先预测，再用前面的沙盒核对：

1. add 之后又改了文件，commit 会保存哪一版？
2. origin/main 比 main 新，fetch 以后你的文件会立刻改变吗？
3. 一笔提交已经被队友拿走，为什么撤销时更适合留下反向提交？

解释里如果出现工作区、暂存区和提交图，你已经开始用模型决定动作，而不只是记命令。答错也很好：回到对应一课，只查那个没有对上的环节。

## 接下来

沙盒里的 Git 是照着真实 Git 的输出和行为写的，但它毕竟只有一层文件夹、一小撮命令。真正的训练是：建一个 `play` 目录，`git init`，把这七课的组合拳打一遍；然后回到你的项目里，从 `git status` 开始。

:::fold[真实终端的起步准备]
示例面向 Git Bash 或 Linux / macOS shell，建议 Git 2.28 及以上，这样 `git init -b main` 才可用。目录名已经存在就换一个：

```bash
mkdir git-play
cd git-play
git init -b main
git config user.name "Practice User"
git config user.email "practice@example.com"
```

这两条身份配置只作用于这个练习仓库，不是 GitHub 登录。接着用编辑器写 `note.txt`，执行 `git add note.txt` 和 `git commit -m "写下第一句"`。改第二句之前先 `git diff`。沙盒里的 `edit 文件` 是辅助命令，真实终端用你自己的编辑器。
:::
