想象你在笔记里搜到一句话：

> 文件改坏了，用 `git restore` 回到上次提交。

短、好记、看起来有用。你照做，文件却没有回到想要的版本。

问题不只是这句话不够严谨。它丢掉了写下它时的状态：文件有没有暂存过？想保留什么？“回去”究竟指哪个版本？那一次操作为什么看起来成功？

**笔记最容易失效的地方，不是结论写错了，而是结论被拆离了成立条件。**

## 别把“我当时懂了”当成存档格式

工作时，很多信息暂存在脑子里。你知道正在改哪个文件，刚才运行了什么，也记得哪一次输出不对。于是记录时自然省略：“改成这样就好了。”

一周后，那个上下文已经不存在。“这样”没有指代，“好了”没有验收标准，剩下的只是一个动作。

如果笔记只服务于十分钟后的你，这可能已经够用。但如果你希望它能指导下一次操作，或者成为公开文章，它就需要携带一点原本存在于脑中的上下文。

这里的目标不是写下所有过程，而是让读者能重建：**当时在回答什么问题，凭什么接受这个答案。**

## 给那句 Git 备忘加一个反例

构造一个最小场景：

1. 提交里保存的是 A。
2. 把文件改成 B，执行 `git add`。
3. 再把文件改成 C，不暂存。
4. 执行不带其他选项的 `git restore 文件`。

现在工作区会变成什么？是 **B，不是 A**。因为这个命令默认从暂存区恢复工作区。之前看起来像“回到上次提交”，只是因为当时暂存区恰好与提交相同。

这一个反例，比补上一段“Git 很复杂，要小心”更有用。它明确指出了原句在哪个条件下失效。

更好的笔记不必很长：

> **问题：**只想丢弃未暂存修改，保留已经暂存的版本。
>
> **状态：**HEAD=A，暂存区=B，工作区=C。
>
> **动作：**`git restore 文件`。
>
> **结果：**工作区变为 B，暂存区仍为 B，HEAD 仍为 A。
>
> **边界：**这不是“恢复到上次提交”的通用命令，也不保证丢弃的 C 可以找回。若目的是取消暂存，应另看 `--staged`。

读者既能用它，也能看出什么时候不该用它。完整可执行的学习路径见 [Git 教程](../progressive-git/index.md)。

## 最值得保存的，通常是四类信息

### 一、问题，而不是知识点标题

“Git restore 用法”是一个工具分类。“误暂存了文件，怎样取消暂存但不丢内容？”是一个可以判断是否解决的问题。

后一种标题并不总是更短，但更接近未来检索时脑子里的句子。工具名适合标签，具体问题适合标题与开头。

同样，“坐标变换笔记”不如“为什么正逆变换都能往返，目标点却仍然错了？”后者把读者带到真正值得理解的矛盾里。

### 二、能区分解释的证据

“试了很多次终于好了”保存了情绪，没有保存判断依据。

在[坐标变换的例子](../debugging-coordinate-frames/index.md)里，最关键的记录不是“用了转置”，而是：原点测试通过，非零基向量测试失败。这条差异把注意力从平移带到了旋转方向。

不必把每一次失败尝试都写进正文。优先保存那个让你**排除一个解释、接受另一个解释**的观察。如果没有这样的观察，就诚实写“暂时相关，尚未确认原因”。

### 三、结论的适用范围

“耗时减少了 20%”还不够。输入规模、硬件、预热、是否包含加载时间，都可能影响这个数字。

“在这个输入、这个计时范围下，从 10 秒到 8 秒”至少让别人知道数字在比较什么。再补上重复次数和波动，才开始接近一份可评价的测量。

适用范围不是给结论加一串免责声明，而是指出：**换掉哪个条件，就应该重新检查。**

### 四、下一次如何发现它过期

把日期写在顶部很有用，但日期不能自动说明是否失效。一条两年前的数学恒等式可能仍然可靠，一条昨天的部署步骤可能已经被配置变更推翻。

更有效的维护提示是：“依赖某个选项的默认值，升级后核对手册”；“仅测试了普通文件，符号链接未覆盖”；“测试集权重改变后，需要重算结果”。

这让未来的你知道要验证哪里，而不是因为文章旧就整篇重写，或因为写得详细就全盘相信。

## 让页面元素承担工作，而不是装饰态度

笔记本式网站很容易让人多放便利贴、标记和折叠。问题是，一页到处高亮，实际上等于没有层次。

在这套写法里，可以给每种元素一个有限职责：

| 元素 | 合适的用途 | 不适合的用途 |
| --- | --- | --- |
| 页边批注 | 主线之外的定义、例外、补充来源 | 塞入理解下一段必须知道的前提 |
| 警告便利贴 | 不可逆操作、安全与数据边界 | 给每段都加“重点” |
| 折叠答案 | 先思考再核对的自测 | 把关键结论藏起来制造点击 |
| 代码块 | 可执行步骤或精确输出，标明两者区别 | 没有环境、输入和预期的半段咒语 |
| 表格 | 并列比较相同维度 | 把一篇连续论证切成碎片 |

交互也一样。让读者先猜，再改变一个输入，看到与猜测不同的结果，它就承担了教学任务。如果只是把正文换成点击翻页，未必值得增加加载与维护成本。

## 公开文章，比私人备忘多一个责任

私人笔记可以写“昨天那份数据”，公开文章不行。公开读者没有昨天，也没有那份数据。

发布前至少做三次区分：

- **实际观测与构造例子。** 为解释原理编一组数字完全合理，但要标明，不要写成亲历实验。
- **输出与解释。** “程序返回 1”是观察；“因为没有匹配项”是结合语境得到的解释；“所以所有非零都表示故障”则是错误推广。
- **来源与验证。** 链接官方文档不等于自己跑过；跑通一次也不等于适用于所有平台。分别说明做过什么。

例如[成功率评估样本](../../academic/success-rate-is-not-evidence/index.md)给出了原始计数和复算脚本，同时明确它是教学构造、区间依赖独立试验假设、加权差值只是点估计。这些边界不是削弱文章，而是让它有可检查的形状。

:::postit[一个简单的发布检查]{question}
如果读者只复制了最显眼的代码，会不会产生我没有提醒的损失？

如果读者只记住最醒目的结论，会不会把一个局部观察当成普遍规律？
:::

## 也别把每张便条都写成论文

这套方法有成本：保存输入、整理步骤、核对来源，都占时间。不是每条记录都值得这样做。

一个实用区分是：

- **临时提醒：**“下午确认版本号。”完成即可删，不需要论证。
- **可复用操作：**“升级后怎样恢复配置。”保留前提、步骤、验收和回退办法。
- **对外主张：**“这个方法更可靠。”需要证据、比较条件、反例与边界。

标准应该跟随误用成本。忘掉一家咖啡店的营业时间，代价通常很小；误记一条清理磁盘的命令，代价可能很大。后者值得更多验证。

有时最好的决定是只留一句“尚未确认，不作为操作依据”，而不是为了填满模板，拼出一个看似完整的解释。

## 一个可以直接使用的短模板

```text
问题：在什么条件下，什么结果与预期不同？
现场：最小输入、版本、配置、原命令。
证据：实际输出；能够区分假设的测试。
结论：改了什么，为什么，改后如何验收。
边界：没有验证什么，哪个条件改变后要重查。
```

也可以下载 [可编辑的证据笔记模板](./attachments/evidence-note.txt)。没有需要就删字段，别为模板制造内容。

**现在做一个小练习：**打开最近一篇写着“解决了”“有效”“更快”的笔记，只补三句话：当时的输入是什么？怎样判断它好了？在哪种情况下这条结论可能不成立？

如果三句都写不出来，不一定意味着当时的工作没有价值。它只是告诉你，当前留下的是一个记忆提示，还不是可以交给别人的证据。

一周后还能用的笔记，并不是把一周前的你永久保存下来。它只需要留下足够的线索，让新的你不用再从同一个误解开始。
